### Automatisation proposée

Rien n'existe aujourd'hui : pas de script, ni `.zenodo.json`, ni workflow.

- `scripts/zenodo-sync.mjs`, **dry-run par défaut** ; table `_data/zenodo.json`
  (slug → record → concept DOI → hash du texte déposé).
- Rendu PDF de `_site/<article>.html` par Chrome headless (CSS d'impression), sur une instance isolée.
- Détection : hash du **texte normalisé** de l'article. Le md5 du PDF ne sert pas, Chrome le change à chaque rendu.
  Seuil pour ignorer les retouches typographiques.
- Publication par l'API InvenioRDM : `POST /api/records/{id}/versions` → upload des fichiers →
  `PUT …/draft` (métadonnées + lien vers l'URL de l'article) → `POST …/draft/actions/publish`.
- Tests d'abord sur sandbox.zenodo.org. Token local `ZENODO_TOKEN` (deposit:write + deposit:actions).
  Déclenchement **manuel** (`npm run zenodo:sync -- --publish <slug>`), jamais sur push.
- Pièges : la publication est irréversible, chaque version crée un DOI, un seul brouillon à la fois.
  Pour Faisceau et Mécanique, le PDF Zenodo est plus riche que la page : il faut choisir par record.
- L'intégration native GitHub→Zenodo ne convient pas : elle archive tout le dépôt par release,
  pas un record par article.

Sources : https://developers.zenodo.org/ ,
https://inveniordm.docs.cern.ch/reference/rest_api_drafts_records/
